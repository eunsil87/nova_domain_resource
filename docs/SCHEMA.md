# 데이터와 저장 정책

앱 버전은 `package.json`의 `0.1.2`, 기준 기능 명세는 v0.24, JSON 스키마 버전은 `schemaVersion: 1`입니다. 이 셋은 서로 다릅니다.

## 파일

앱 폴더의 `nova-data.json` 한 파일만 생성합니다. 파일이 없을 때는 사용자의 새 워크스페이스 생성 확인을 받습니다. JSON 손상·지원하지 않는 스키마는 자동 초기화하지 않습니다. 초기 데이터 표식 `initialized: true`는 빈 인력 목록도 유효한 기존 데이터라는 뜻입니다.

## 소유 범위

| 필드 | 의미 |
| --- | --- |
| `schemaVersion` | 구조 버전. 현재 1만 지원하며 최신 버전을 임의 변환하지 않음 |
| `saveVersion` | 성공적인 파일 저장마다 1 증가. 쓰기 완료 전에는 증가를 확정하지 않음 |
| `projectName`, `partName` | 한 데이터 묶음의 프로젝트·업무 파트 이름 |
| `companies` | ID·표시명·직원 타입·활성 여부 |
| `roles`, `technologies` | ID·표시명·활성 여부. Focal 등 기본 기능 의미는 ID로 유지 |
| `people` | 확정/TBD 공통 원본, 한 투입당 ID 하나 |
| `plans` | 안별 인력 그룹·상위 그룹·리더·배치 순서 |
| `appliedPlanId` | 적용 안 ID, 정확히 하나 |
| `representativeIds` | 업무 파트 공통 복수 현장대리인. 조합은 인력의 업체·역할·기술 ID에서 파생 |
| `chiefId` | 업무 파트 공통 개발반장 ID 또는 null |
| `targets` | 연도별 목표. 정수 0.001 M/M 단위, null은 미설정 |
| `phases` | 프로젝트에 속한 참고 일정. 인력 기간이나 M/M에 자동 적용하지 않음 |

인력은 `kind`, `name`, `companyId`, `roleId`, `techId`, `start`, `end`, `everStarted`, `extra`를 가집니다. 직원 타입과 M/M, 투입 표시 상태는 저장하지 않고 계산합니다. 종료 미정은 `9999-12-31`, 일반 선택 미입력은 null입니다.

`everStarted`는 시작일을 미래로 정정해도 업체 잠금이 풀리지 않도록 보관하는 최소 상태입니다. 선택 필드 `representativeReleased`는 실제 철수 처리에서 대표 지정을 해제한 뒤 다음 시작 처리에서 같은 인력을 무조건 재선임하지 않도록 합니다. 직접 대표로 다시 지정하면 해제됩니다. 변경 이력·로그가 아닙니다.

`extra`는 `skt`, `doss`, `devdi`, `mydesk`, `local`, `seat`, `memo`를 가지며 미입력은 null입니다. 가사번과 DOSS ID는 접두어를 포함한 문자열, IP는 네 칸을 합친 문자열입니다.

인력 그룹은 `{id, name, members: [인력ID], leaderId}`이며 순서는 members 배열로 보존합니다. 리더는 화면에서 항상 맨 위에 표시합니다. 상위 그룹은 `{id, name, groupIds: [인력그룹ID], leaderId}`입니다. 상위 그룹에 인력 원본을 복제하지 않습니다. 구성안 복사는 그룹/상위 그룹 ID를 새로 발급하고 공통 인력 ID는 그대로 참조합니다.

## 쓰기 순서

1. 파일에서 읽은 원본과 세션/팝업 초안을 구별합니다.
2. 팝업 적용은 작업 사본의 검증·인계·참조 정리를 모두 성공한 뒤 세션을 교체합니다.
3. 시작 처리도 작업 사본에서 수행하며 필요한 선택을 취소하면 파일을 변경하지 않습니다.
4. 쓰기 직전 디스크의 전체 원문을 다시 읽어 읽었을 때의 원문과 비교합니다. 저장 버전 변경뿐 아니라 동일 버전의 외부 편집도 충돌로 처리합니다.
5. 사본의 saveVersion을 올려 `createWritable → write → close`를 완료합니다. 실패하면 가능한 경우 abort하고 기존 세션·저장 기준을 유지합니다.
6. 쓰기 완료 후에만 저장 완료를 표시하고 기준 원문/저장 버전을 갱신합니다.

별도 백업 파일은 생성하지 않습니다. 이 비교는 두 탭이 완전히 동시에 쓰는 모든 경쟁 상태를 차단하지 못하므로 단일 탭 사용이 기본입니다. 스키마 1 이전에 배포한 앱이나 데이터가 없어 이전 형식 마이그레이션은 정의하지 않았습니다.

## 0.1.1 그룹 배치 확장

구성안별 선택 필드 `rootOrder: [ID, ...]`가 상위 그룹과 독립 인력 그룹의 혼합 표시 순서를 보관합니다. 인력 그룹 자체의 ID, 공통 인력 원본, M/M는 바뀌지 않습니다. 상위 그룹 안의 하위 순서는 기존 `groupIds`로 보관합니다.

`rootOrder`가 없는 기존 스키마 1 파일은 상위 그룹 → 독립 그룹의 기존 순서를 유지합니다. 조회만으로 순서를 파일에 추가하지 않습니다. 배치를 편집한 안에서만 새 순서를 기록하고, 그룹 삭제·묶기·해제 후에는 유효한 최상위 항목만 유지합니다. 구성안 복사는 rootOrder의 그룹/상위 그룹 ID도 새 ID로 연결합니다.
